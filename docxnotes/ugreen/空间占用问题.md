# 空间占用问题

针对你提到的“用户数据存储占用空间远低于实际占用空间”这一现象，结合你之前的排查经历，这通常由两大核心原因导致。下面我将这两点展开，为你提供完整的排查和解决思路。

---

## 一、Btrfs 文件系统碎片化（Data Chunk 碎片化）

### 1.1 根本原因：Btrfs 的“先分配，后使用”机制

Btrfs 文件系统以  **“数据区块（Data Chunk）”**  为单位管理存储空间。当你向卷中写入数据时，Btrfs 可能会**一次性分配一个较大的区块**（例如 1GB），即使你只写入了几十 MB，这个区块也已经被“占用”了，无法再分配给其他数据使用。

这种机制在以下场景下会加剧碎片化：

- **频繁写入、删除、修改文件**：每次修改都会触发“写时复制（CoW）”，产生新的数据副本，旧的数据块可能被标记为空闲，但所在的整个数据区块仍然被系统保留。
- **大量小文件写入**：每个小文件都可能触发独立的数据区块分配，导致区块利用率极低。
- **RAID 1 或 RAID 5/6 模式**：为了保证数据冗余，Btrfs 在分配数据区块时会更“粗放”，进一步放大了空间浪费。

### 1.2 典型表现

- **​`df -h`​**​ **或 NAS 界面显示空间已满**（例如 3.6TB/3.6TB）
- **实际文件总大小**（通过 `du -sh /volume1` 统计）却远小于已用空间（例如只有 565GB）
- 执行 **​`btrfs fi us /volume1`​** 时会看到：

  ```
  Data, single: Size: 3.60TiB, Used: 565GiB (约 15%)
  Unallocated: 很小甚至为 0
  ```

  这表明虽然实际数据只用了 565GB，但 Btrfs 已经将**整个 3.6TB 都分配出去了**，所以系统认为空间已满。

### 1.3 解决方案：Btrfs Balance

执行 Balance 操作可以整理这些碎片化的数据区块，将未真正使用的空间释放回“未分配（Unallocated）”池。

**操作步骤**（通过 SSH 以 root 权限执行）：

```bash
# 1. 先查看当前空间分配情况
btrfs fi us /volume1

# 2. 从低阈值开始 Balance（例如使用率低于 5% 的区块）
btrfs balance start -dusage=5 /volume1

# 3. 再次查看空间，如果释放不够，逐步提高阈值
btrfs balance start -dusage=10 /volume1
btrfs balance start -dusage=30 /volume1

# 4. 每次执行后查看效果
btrfs fi us /volume1
```

> ⚠️ **注意**：Balance 操作会占用一定的系统 I/O，建议在 NAS 空闲时进行。新机器数据量少，通常几分钟内就能完成。

## 二、通过 `du` 查询隐藏的应用数据与系统占用

即使 Btrfs 碎片化问题解决了，系统中仍可能存在一些**用户界面不可见的数据**，它们同样会占用大量空间。通过 `du` 命令可以逐层排查。

### 2.1 `du`​ 与 `df` 的差异

- **​`df -h /volume1`​**：显示的是文件系统层面的“已分配”空间（即 Btrfs 已占用的区块大小）。
- **​`du -sh /volume1`​**：统计的是实际文件数据的总大小（递归累加所有文件占用的字节数）。

当 `df`​ 显示的空间远大于 `du` 统计的大小时，说明存在以下可能：

- Btrfs 数据区块碎片化（已在上文解决）
- 存在被删除但仍在被进程占用的文件
- 存在快照（Snapshot）或子卷（Subvolume）占用
- 存在系统或应用在“隐藏目录”中写入的大量数据

### 2.2 排查步骤

#### 第一步：检查被进程占用的“已删除”文件

如果有进程正在读写某个文件，而你删除了它，文件系统会释放目录项，但**磁盘空间不会归还**，直到该进程关闭文件句柄。

```bash
lsof +L1 | grep /volume1
```

如果输出有内容（特别是状态为 `(deleted)`​ 的大文件），说明有进程正在占用已删除的文件。**重启对应的服务或进程**后，这部分空间就会被释放。

#### 第二步：查看 Btrfs 快照和子卷

快照会保留历史数据块，即使你在当前文件系统中删除了文件，快照中的副本仍然占用空间。

```bash
# 列出所有子卷和快照
btrfs subvolume list -t /volume1

# 查看引用计数（判断是否有大量共享数据）
btrfs qgroup show -p -c -r /volume1
```

如果发现不需要的快照，可以通过以下命令删除（谨慎操作）：

```bash
btrfs subvolume delete /volume1/.snapshots/<snapshot_name>
```

#### 第三步：逐层排查隐藏的大目录

进入 `/volume1` 根目录，排除快照目录，统计各子目录的真实占用：

```bash
cd /volume1
du -sh --exclude='.snapshot' --exclude='#snapshot' * 2>/dev/null | sort -hr | head -20
```

重点关注以下**常见隐藏目录**（UI 中可能不可见）：

|目录路径|可能来源|占用说明|
| ----------| ---------------| --------------------------|
|`/volume1/.@__ugreen`|UGOS 系统数据|系统配置、回收站残留|
|`/volume1/@docker`|Docker 数据|容器镜像、容器卷、日志|
|`/volume1/@appshare`|应用共享数据|第三方应用产生的数据|
|`/volume1/@cloudsync`|云同步缓存|同步任务的本地缓存|
|`/volume1/@download`|下载缓存|临时下载文件|
|`/volume1/@logs`|日志文件|系统或应用日志|
|`/volume1/.Trash-*`|回收站|即使 UI 清空，可能有残留|
|`/volume1/@tmp`|临时文件|各类临时缓存|

#### 第四步：进一步深入可疑目录

如果在第三步发现了占用较大的隐藏目录，继续深入查看：

```bash
cd /volume1/@docker
du -sh * | sort -hr | head -10
```

## 三、完整的排查流程总结

针对“用户数据存储占用空间远低于实际占用空间”的问题，建议按以下顺序操作：

```
┌─────────────────────────────────────────────────────────────┐
│  1. 确认症状：df -h /volume1  和  du -sh /volume1 对不上   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 检查 Btrfs 分配情况：btrfs fi us /volume1             │
│     → 如果 Data Size 远大于 Used，执行 Balance             │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 检查被删除但未释放的文件：lsof +L1 | grep /volume1   │
│     → 如有，重启相关进程                                   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  4. 检查快照：btrfs subvolume list /volume1              │
│     → 如有多余快照，删除释放空间                           │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  5. 逐层 du 排查隐藏目录（@docker、@cloudsync 等）       │
│     → 定位具体占用空间的应用或系统目录                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  6. 如果以上都排查完，空间仍未恢复，考虑执行完整 Balance  │
│     btrfs balance start -dusage=50 /volume1               │
│     （或联系绿联技术支持进一步分析）                       │
└─────────────────────────────────────────────────────────────┘
```

## 四、预防建议

1. **定期执行 Balance**：尤其是频繁写入删除的场景，建议每季度执行一次 `btrfs balance start -dusage=30 /volume1`。
2. **控制快照数量**：快照数量越多，碎片化程度越高，建议仅保留最近几天的快照。
3. **监控隐藏目录**：定期检查 `@docker`​、`@cloudsync` 等目录的占用，避免缓存无限增长。
4. **开启 Btrfs 空间回收**：UGOS Pro 系统在 2026 年 5 月更新中增加了“Btrfs 空间回收”功能，可在 UI 中一键操作。
